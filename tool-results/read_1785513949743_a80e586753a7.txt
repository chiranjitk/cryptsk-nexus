   802→### BUG-B2: Plan Migration Does Not Update radusergroup (CRITICAL)
   803→- **Tests Exposed:** T4.2
   804→- **Root Cause:** `POST /api/plans/migrate` updates `subscriber.planId` and `subscriber.radiusGroupId` in the application database, but does not execute an `UPDATE radusergroup SET groupname = ... WHERE username = ...` statement. The `radiusSynced` count in the response is always 0.
   805→- **Impact:** After migration, subscribers authenticate at the OLD plan's speed. The app shows the new plan but RADIUS enforces the old one.
   806→- **Fix Required:** In the migration handler, after updating each subscriber, execute `UPDATE radusergroup SET groupname = '<new-group>' WHERE username = '<subscriber-serviceUsername>'`. Also update `radreply` for per-user rate limits.
   807→
   808→### BUG-B-NEW-3: /api/aaa/users POST Fails with 500 (HIGH)
   809→- **Tests Exposed:** T2.4 (also blocked T2.5, T2.6, T2.7)
   810→- **Root Cause:** The AAA users creation route attempts to insert a `createdAt` column into the raw `radcheck` table, which does not have that column. The `radcheck` table is a FreeRADIUS schema table managed outside of Prisma.
   811→- **Fix Required:** Remove `createdAt` from the INSERT statement for raw RADIUS tables, or add the column to the `radcheck` table definition.
   812→
   813→### BUG-B-NEW-4: Data Limit Not Synced to RADIUS on Plan Creation (HIGH)
   814→- **Tests Exposed:** T2.9, T3.5b
   815→- **Root Cause:** The `syncGroupToFreeRADIUS` function supports syncing `ChilliSpot-Max-Total-Octets` to `radgroupreply`, but the plan creation route never passes the `dataLimitMb` parameter to this function.
   816→- **Fix Required:** In the plan creation handler, when a plan has `dataLimitGb > 0`, call `syncGroupToFreeRADIUS` with `dataLimitMb: plan.dataLimitGb * 1024`.
   817→
   818→### BUG-B-NEW-6: Duplicate Billing Periods Not Prevented (HIGH)
   819→- **Tests Exposed:** T5.8
   820→- **Root Cause:** `POST /api/invoices/bulk-generate` does not check for existing invoices in the same billing period for the same subscriber. Running it twice creates duplicate invoices.
   821→- **Fix Required:** Add a check before creating each invoice: `SELECT COUNT(*) FROM "Invoice" WHERE "subscriberId" = ? AND "issueDate" = ?`. Skip if count > 0.
   822→
   823→### BUG-B-NEW-7: Plan Speed Update Not Synced to RADIUS (HIGH)
   824→- **Tests Exposed:** T3.6b
   825→- **Root Cause:** The `PUT /api/plans/<id>` route updates the Plan record in the database but does not call `syncGroupToFreeRADIUS` to update the corresponding `radgroupreply` entry.
   826→- **Fix Required:** After updating the plan, call `syncGroupToFreeRADIUS` with the new speed values to update `Mikrotik-Rate-Limit` in `radgroupreply`.
   827→
   828→### BUG-B-NEW-8: Plan DELETE Leaves Orphaned RADIUS Group (HIGH)
   829→- **Tests Exposed:** T3.8b
   830→- **Root Cause:** The `DELETE /api/plans/<id>` route deletes the Plan and RadiusGroup records from the application database but does not clean up `radgroupcheck` and `radgroupreply` entries in FreeRADIUS tables.
   831→- **Fix Required:** Before or after deleting the RadiusGroup, execute `DELETE FROM radgroupcheck WHERE groupname = ?` and `DELETE FROM radgroupreply WHERE groupname = ?`.
   832→
   833→### BUG-B-NEW-9: Floating-Point Precision Prevents PAID Status (MEDIUM)
   834→- **Tests Exposed:** T6.3
   835→- **Root Cause:** After paying the exact grand total, the invoice `balanceAmount` is `1.13686837721616e-13` instead of exactly 0 due to floating-point arithmetic. The status check `balanceAmount === 0` fails.
   836→- **Fix Required:** Use epsilon comparison: `if (balanceAmount <= 0.01) { status = 'PAID' }`, or round to 2 decimal places before comparison.
   837→
   838→### BUG-B-NEW-10: /api/billing record_payment Allows Overpayment (HIGH)
   839→- **Tests Exposed:** T6.6
   840→- **Root Cause:** The `/api/payments` endpoint validates against outstanding balance, but the `/api/billing` endpoint's `record_payment` action does not perform this validation. Payment amount is accepted unconditionally.
   841→- **Fix Required:** Add the same balance validation logic from `/api/payments` to the billing endpoint's `record_payment` handler.
   842→
   843→### BUG-B-NEW-11: loginRestriction Columns Missing from DB Schema (HIGH)
   844→- **Tests Exposed:** T7.1, T7.2, T7.3
   845→- **Root Cause:** The `loginRestriction` and `loginRestrictionValue` columns are not defined in the Prisma schema or the PostgreSQL `Subscriber` table. The API accepts these fields silently but they are not persisted.
   846→- **Fix Required:** Run a Prisma migration to add `loginRestriction` (enum: all, subnet, ip) and `loginRestrictionValue` (String?) columns to the Subscriber model.
   847→
   848→### BUG-B-NEW-17: GET /api/aaa/groups/[groupname] Column Name Case Mismatch (HIGH)
   849→- **Tests Exposed:** T10.10
   850→- **Root Cause:** The SQL query uses `ug."groupName"` (camelCase, double-quoted) but the `radusergroup` table has a lowercase `groupname` column. PostgreSQL treats quoted identifiers as case-sensitive.
   851→- **Fix Required:** Change `ug."groupName"` to `ug.groupname` in the GET group-by-name query.
   852→
   853→### BUG-M13-001: action Field Naming Collision in Time Access Policies (HIGH)
   854→- **Tests Exposed:** T13.1, T13.2, T13.3, T13.4
   855→- **Root Cause:** The POST endpoint destructures `action` from the request body for both the operation type (`create-policy`) and the policy action type (`ALLOW`/`BLOCK`/`RATE_LIMIT`). Both resolve to the same `body.action` field.
   856→- **Fix Applied:** Changed to read `body.policyAction` for the policy action type. Fix works in `next dev` but Turbopack production build did not fully pick up the change. Needs rebuild.
   857→
   858→### BUG-M13-002: GET Time Access Policies Fail in Turbopack Production Build (HIGH)
   859→- **Tests Exposed:** T13.7, T13.8, T13.10 (update)
   860→- **Root Cause:** Turbopack standalone output has issues serializing Prisma `Json` column type (`daysOfWeek`) during server-side rendering. Works in `next dev` mode.
   861→- **Fix Required:** Investigate Turbopack serialization of Prisma Json fields. May need to add explicit JSON serialization or use a different approach for the `daysOfWeek` column.
   862→
   863→### BUG-M12-001: SQL Injection Returns 500 Instead of 400 (MEDIUM)
   864→- **Tests Exposed:** T12.1
   865→- **Root Cause:** Input validation for `serviceUsername` does not reject SQL metacharacters. Prisma ORM prevents actual SQL injection, but the unhandled error bubbles up as 500.
   866→- **Fix Required:** Add validation regex for `serviceUsername` to reject special characters (e.g., `/^[a-zA-Z0-9._-]+$/`). Return 400 for invalid input.
