   137→# 3. PRODUCT MISSION
   138→
   139→Build CRYPTSK Nexus as a modern, production-ready OSS/BSS platform for ISPs,
   140→broadband operators, enterprise networks, WiFi operators, FTTH/GPON
   141→operators, and managed network providers.
   142→
   143→Cryptsk must be:
   144→
   145→-   Modular
   146→-   Resource efficient
   147→-   Production ready
   148→-   Scalable
   149→-   Secure
   150→-   API-first
   151→-   Multi-tenant capable
   152→-   RBAC capable
   153→-   Observable
   154→-   Testable
   155→-   Upgradeable
   156→-   Maintainable
   157→-   License/module aware
   158→-   Suitable for small deployments and large deployments
   159→-   Capable of running only the modules actually enabled by the customer
   160→
   161→The final product must NOT behave like a single giant application where
   162→every feature is loaded and initialized regardless of whether it is
   163→being used.
   164→
   165→The architecture must support selective module activation.
   166→
   167→## Two-Plane Product Architecture
   168→
   169→CRYPTSK Nexus consists of two tightly integrated but operationally distinct
   170→planes:
   171→
   172→``` text
   173→                    CRYPTSK NEXUS
   174→                           |
   175→          +----------------+----------------+
   176→          |                                 |
   177→          ▼                                 ▼
   178→   OSS/BSS MANAGEMENT PLANE          NETWORK/GATEWAY PLANE
   179→   Next.js / Application             DPDK + VPP
   180→   Customer / Billing / UI            Session Enforcement
   181→   RBAC / Audit / Reporting           NAT / ACL / QoS
   182→   Configuration / Analytics          Packet Forwarding
   183→          |                                 |
   184→          +---------------+-----------------+
   185→                          |
   186→                  Shared Control Contracts
   187→                 APIs / Events / Policies
   188→                 Session / Subscriber Model
   189→```
   190→
   191→The OSS/BSS management plane MUST NOT perform packet forwarding or
   192→subscriber packet enforcement.
   193→
   194→The network/gateway plane MUST NOT depend on the Next.js UI for packet
   195→processing.
   196→
   197→This separation is mandatory for the 100K-session / 50 Gbps-class
   198→product target.

   608→## Module Disablement Must Be Real
   609→
   610→Module disablement must operate at multiple layers.
   611→
   612→When a module is disabled:
   613→
   614→1.  Its navigation is unavailable.
   615→2.  Its protected routes reject access.
   616→3.  Its frontend module is not unnecessarily loaded.
   617→4.  Its module initialization code does not execute.
   618→5.  Its workers do not start.
   619→6.  Its scheduled jobs do not run.
   620→7.  Its external connections are not opened.
   621→8.  Its polling loops do not run.
   622→9.  Its module-specific caches are not initialized unnecessarily.
   623→10. Its event consumers are inactive.
   624→
   625→The backend must enforce disablement. Hiding the menu is NOT sufficient.
   626→
   627→## Resource Reduction Proof Requirement
   628→
   629→Cryptsk must provide measurable evidence that optional modules can be
   630→disabled without unnecessary runtime resource consumption.
   631→
   632→For selected modules, establish measurements for:
   633→
   634→Module ENABLED: - process/worker count - runtime RAM - CPU utilization
   635→under defined workload - open connections - active timers/jobs -
   636→relevant bundle/build contribution
   637→
   638→Module DISABLED: - process/worker count - runtime RAM - CPU
   639→utilization - open connections - active timers/jobs - frontend loading
   640→behavior
   641→
   642→Do not claim that disabling a module reduces build memory unless it is
   643→actually excluded from the relevant build graph. Runtime lazy loading
   644→and build-time exclusion are separate concerns.
   645→
   646→## Build-Time Module Isolation
   647→
   648→Where practical, the architecture must support build-time module
   649→isolation so that optional modules do not unnecessarily increase every
   650→build target.
   651→
   652→Use appropriate techniques such as:
   653→
   654→-   code splitting
   655→-   dynamic imports
   656→-   conditional module composition
   657→-   separate worker entry points
   658→-   package boundaries
   659→-   production bundle analysis
   660→
   661→Do not create a complicated build system merely to satisfy this
   662→requirement. Measure first and use the simplest maintainable solution.
   663→

   732→# 4A. 100K CONCURRENT SESSION CAPACITY & SCALABILITY REQUIREMENT
   733→
   734→Cryptsk must be architected from Day Zero with a production capacity
   735→target of at least:
   736→
   737→**100,000 CONCURRENT ACTIVE SUBSCRIBER/DEVICE SESSIONS**
   738→
   739→This is a production architecture target, not a requirement for the 4 GB
   740→development sandbox.
   741→
   742→The initial certified deployment profile may be 50,000 concurrent
   743→sessions, but the software architecture MUST NOT contain a hard 50K
   744→ceiling.
   745→
   746→## Capacity Dimensions
   747→
   748→The architecture must independently account for:
   749→
   750→``` text
   751→C1 = concurrent active sessions
   752→C2 = authentication requests/sec
   753→C3 = accounting events/sec
   754→C4 = CoA/sec
   755→C5 = Disconnect/sec
   756→C6 = new sessions/sec
   757→C7 = NAT/flow count
   758→C8 = packets/sec
   759→C9 = throughput
   760→C10 = policy/VPP operations/sec
   761→C11 = database writes/sec
   762→C12 = monitoring/events/sec
   763→```
   764→
   765→100,000 sessions does NOT mean:
   766→
   767→``` text
   768→100k threads
   769→100k processes
   770→100k SQL connections
   771→100k VPP API connections
   772→100k policy objects
   773→100k DB transactions/sec
   774→```
   775→
   776→## Session Architecture
   777→
   778→Live session state MUST be owned by the Session Engine / AAA session
   779→subsystem, not by the browser, Next.js process, PostgreSQL packet path,
   780→or FreeRADIUS configuration.
   781→
   782→The live-session architecture must support:
   783→
   784→``` text
   785→session_id
   786→subscriber/account identity
   787→username
   788→NAS/access source
   789→MAC/device identity
   790→IPv4/IPv6
   791→VLAN
   792→VRF
   793→policy/profile IDs
   794→bandwidth/QoS
   795→ACL
   796→NAT profile
   797→session timers
   798→accounting state
   799→counters
   800→owner node
   801→session epoch/generation
   802→event sequence
   803→```
   804→
   805→Live state should be compact and in memory, with durable
   806→recovery/snapshot information persisted separately.
   807→
   808→Historical sessions/accounting must use database-optimized storage.
   809→
   810→## Accounting Scale
   811→
   812→At 100,000 active sessions:
   813→
   814→``` text
   815→5-minute interim:
   816→100,000 / 300 ≈ 333 events/sec
   817→
   818→1-minute interim:
   819→100,000 / 60 ≈ 1,667 events/sec
   820→```
   821→
   822→Accounting ingestion MUST therefore be asynchronous/buffered where
   823→appropriate, bounded, observable, retryable, and idempotent.
   824→
   825→Do not synchronously write every accounting event through the
   826→UI/application request path.
   827→
   828→## Horizontal Scalability
   829→
   830→Production must permit independent scaling of:
   831→
   832→``` text
   833→API/UI workers
   834→AAA/authentication workers
   835→Session Engine workers
   836→Accounting workers
   837→Monitoring workers
   838→Reporting workers
   839→```
   840→
   841→The dataplane scales separately through VPP workers, NIC queues, RSS,
   842→CPU affinity, NUMA locality, and hardware capacity.
   843→
   844→## Capacity Testing
   845→
   846→The test methodology must progressively validate:
   847→
   848→``` text
   849→10K
   850→25K
   851→50K
   852→75K
   853→100K
   854→```
   855→
   856→and measure authentication latency, accounting latency, session
   857→operations, CPU, RAM, database latency, queue depth, VPP programming
   858→latency, packet loss, PPS, throughput, and recovery behavior.
   859→
   860→50K is the initial certification profile.
   861→
   862→100K is the architectural capacity target.
   863→
   864→50 Gbps is a hardware-qualified dataplane target, not a distro-only or
   865→software-only guarantee.
