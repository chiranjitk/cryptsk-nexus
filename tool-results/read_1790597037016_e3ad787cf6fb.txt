     8→
     9→# 1. PURPOSE
    10→
    11→This document defines the interface contract between the Cryptsk UI, management/application services, gateway control components, AAA, Session Engine, integrations, workers, and durable storage.
    12→
    13→The objective is not to reproduce the legacy `501 route.ts` files one-for-one. The objective is to preserve the complete product capability surface while creating stable, versioned, typed, observable, secure interfaces.
    14→
    15→The API architecture MUST support:
    16→
    17→- the full feature catalogue;
    18→- the three deployment modes;
    19→- 100,000 concurrent live sessions;
    20→- management-plane horizontal scaling;
    21→- gateway control-plane recovery;
    22→- asynchronous work where latency-sensitive operations must not block;
    23→- strong validation and authorization;
    24→- idempotent operational commands;
    25→- auditability;
    26→- backward-compatible evolution;
    27→- clear distinction between configuration, commands, queries, and events.
    28→
    29→The API layer is a control interface. It is never the packet-processing path.
    30→

    50→# 3. INTERFACE TAXONOMY
    51→
    52→Cryptsk uses four interface classes.
    53→
    54→## 3.1 External management API
    55→
    56→Used by:
    57→
    58→- Next.js/React management UI
    59→- self-care UI
    60→- approved automation clients
    61→- customer integrations
    62→- reporting/export clients
    63→
    64→Preferred style:
    65→
    66→- HTTPS
    67→- REST/JSON for public management contracts
    68→- explicit API versioning
    69→- typed request/response schemas
    70→
    71→## 3.2 Internal synchronous service interface
    72→
    73→Used when a synchronous decision is required between trusted internal components.
    74→
    75→Examples:
    76→
    77→- Management API → domain service
    78→- Policy Engine → Session Engine
    79→- Session Engine → VPP Adapter
    80→- gateway controller → VPP control component
    81→
    82→The implementation MAY use gRPC or another strongly typed RPC mechanism, but the domain contract MUST remain transport-independent.
    83→
    84→## 3.3 Asynchronous event interface
    85→
    86→Used for:
    87→
    88→- accounting ingestion
    89→- notifications
    90→- audit consumers
    91→- analytics
    92→- reporting pipelines
    93→- AI consumers
    94→- integration delivery
    95→- long-running jobs
    96→- lifecycle propagation
    97→
    98→Events MUST be versioned schemas, not arbitrary internal JSON objects.
    99→
   100→## 3.4 Gateway command interface
   101→
   102→Used by trusted control-plane components to request dataplane changes.
   103→
   104→Examples:
   105→
   106→- create subscriber dataplane state
   107→- update bandwidth profile
   108→- attach/detach ACL
   109→- allocate/release address
   110→- apply NAT policy
   111→- remove session state
   112→- reconcile VPP objects
   113→
   114→The gateway command path uses VPP Binary API / GoVPP or an approved adapter. `vppctl` is not the normal runtime provisioning API.

   118→# 4. API DESIGN PRINCIPLES
   119→
   120→Every production API MUST be:
   121→
   122→- authenticated;
   123→- authorized;
   124→- validated;
   125→- observable;
   126→- documented;
   127→- deterministic for the same valid input where applicable;
   128→- explicit about partial failure;
   129→- safe to retry where the operation may be retried;
   130→- protected against unbounded resource consumption.
   131→
   132→APIs MUST NOT expose database implementation details as their primary contract.
   133→
   134→Do not expose:
   135→
   136→- raw Prisma model names as the only interface definition;
   137→- direct SQL endpoints;
   138→- filesystem paths;
   139→- internal secrets;
   140→- VPP object handles without a stable domain abstraction;
   141→- internal service credentials;
   142→- raw password hashes.

   157→

   190→# 6. STANDARD HTTP SEMANTICS
   191→
   192→| Method | Meaning | Typical use |
   193→|---|---|---|
   194→| GET | Read | list/detail/report query |
   195→| POST | Create / command | create resource or initiate operation |
   196→| PUT | Replace | full deterministic replacement |
   197→| PATCH | Partial update | targeted mutable fields |
   198→| DELETE | Retire/remove | deletion where safe and meaningful |
   199→
   200→Mutation endpoints MUST state whether the operation is:
   201→
   202→- transactional;
   203→- asynchronous;
   204→- eventually consistent;
   205→- idempotent;
   206→- reversible;
   207→- auditable.

   211→# 7. COMMON REQUEST HEADERS
   212→
   213→Recommended:
   214→
   215→```text
   216→Authorization: Bearer <token>
   217→Content-Type: application/json
   218→Accept: application/json
   219→X-Correlation-ID: <uuid>
   220→Idempotency-Key: <unique-value>
   221→If-Match: <etag>             # where optimistic concurrency is applicable
   222→```
   223→
   224→`X-Correlation-ID` is created at the edge if absent and propagated through all internal calls, logs, traces, jobs, and events.
   225→
   226→`Idempotency-Key` is REQUIRED for externally retriable financial and operational commands where duplicate execution could cause damage.

   314→# 10. PAGINATION / FILTERING / SORTING
   315→
   316→Default collection behavior MUST be bounded.
   317→
   318→No endpoint may return an unbounded subscriber, session, accounting, log, or audit collection.
   319→
   320→Preferred query contract:
   321→
   322→```text
   323→?page=1&page_size=50
   324→?sort=-created_at,name
   325→?status=ACTIVE
   326→?area_id=...
   327→?search=...
   328→?from=...
   329→?to=...
   330→```
   331→
   332→Maximum page size MUST be enforced by the server.
   333→
   334→Large exports use asynchronous jobs rather than forcing the browser to hold millions of rows.
   335→

   338→# 11. QUERY VS COMMAND RULE
   339→
   340→The API MUST distinguish read-heavy queries from state-changing commands.
   341→
   342→Example:
   343→
   344→```text
   345→GET  /api/v1/sessions
   346→POST /api/v1/sessions/{id}:disconnect
   347→```
   348→
   349→A GET request MUST NOT perform a hidden state mutation.
   350→
   351→An endpoint that merely "refreshes" cached telemetry MUST still define whether it triggers an expensive operation.

   514→# 13. SUBSCRIBER LIFECYCLE API
   515→
   516→A subscriber workflow is not a single POST.
   517→
   518→Canonical lifecycle:
   519→
   520→```text
   521→Create customer
   522→  ↓
   523→Create subscriber
   524→  ↓
   525→Create service/subscription
   526→  ↓
   527→Attach plan
   528→  ↓
   529→Resolve access profile
   530→  ↓
   531→Allocate/prepare network resources
   532→  ↓
   533→Provision AAA identity
   534→  ↓
   535→Activate service
   536→  ↓
   537→Observe authentication/session
   538→  ↓
   539→Bill/account
   540→  ↓
   541→Suspend/modify/terminate
   542→```
   543→
   544→The API MUST return resource state accurately. It must not report `ACTIVE` while required provisioning failed.
   545→

   548→# 14. PLAN → POLICY API
   549→
   550→Plans are business objects. Gateway policies are enforcement objects.
   551→
   552→The API flow is:
   553→
   554→```text
   555→Plan
   556→ → Service Policy
   557→ → Network Policy
   558→ → Compiled Policy Version
   559→ → Gateway Apply
   560→```
   561→
   562→A plan update MUST create or identify a versioned effective policy. Existing sessions follow the configured policy change semantics:
   563→
   564→- immediate CoA/apply;
   565→- next login;
   566→- scheduled effective time;
   567→- manual rollout.
   568→
   569→This rule must be explicit per policy type.

   634→# 17. ACCOUNTING API
   635→
   636→Accounting ingestion must tolerate:
   637→
   638→- duplicates;
   639→- delayed records;
   640→- out-of-order records;
   641→- interim updates;
   642→- NAS restarts;
   643→- session reconnects;
   644→- missing stop events;
   645→- counter resets;
   646→- clock skew.
   647→
   648→Never treat a single NAS packet as the complete accounting truth without reconciliation rules.
   649→
   650→Canonical objects:
   651→
   652→- accounting event;
   653→- session counter sample;
   654→- normalized session usage;
   655→- final session record.
   656→
   657→Accounting ingestion SHOULD be append-oriented, with deterministic aggregation and dedupe keys.

   661→# 18. IDEMPOTENCY
   662→
   663→Operations requiring idempotency include:
   664→
   665→- subscriber provisioning;
   666→- service activation;
   667→- plan migration;
   668→- invoice generation;
   669→- payment creation;
   670→- refunds;
   671→- gateway session create;
   672→- gateway session delete;
   673→- policy apply;
   674→- IP assignment;
   675→- notification sending where duplicate delivery is harmful;
   676→- integration webhooks;
   677→- backup jobs;
   678→- batch jobs.
   679→
   680→Idempotency records MUST have an explicit retention policy.
   681→
   682→The implementation MUST distinguish:
   683→
   684→```text
   685→same key + same request → same result
   686→same key + different request → conflict
   687→```
   688→
   689→---
   690→
   691→# 19. CONCURRENCY / VERSIONING
   692→
   693→Mutable business resources SHOULD support optimistic concurrency where concurrent edits are possible.
   694→
   695→Use either:
   696→
   697→- numeric version;
   698→- entity revision;
   699→- ETag/If-Match;
   700→- deterministic update timestamp with server-side compare.
   701→
   702→The API must not silently overwrite a newer policy or billing document because two operators edited the same screen.
   703→

   705→
   706→# 20. LONG-RUNNING OPERATIONS
   707→
   708→Use an operation resource for:
   709→
   710→- mass provisioning;
   711→- bulk invoice generation;
   712→- report generation;
   713→- exports;
   714→- data imports;
   715→- device discovery;
   716→- diagnostics;
   717→- backup/restore;
   718→- large reconciliation;
   719→- gateway rebuild/reconcile.
   720→
   721→Pattern:
   722→
   723→```text
   724→POST /resource:command
   725→        ↓
   726→202 Accepted
   727→        ↓
   728→operation_id
   729→        ↓
   730→GET /operations/{id}
   731→```
   732→
   733→Optional websocket/SSE streaming may provide progress but MUST NOT be the only way to observe job state.

   821→# 23. OUTBOX / DELIVERY RULE
   822→
   823→Any durable business transaction that also needs event publication MUST use an atomic outbox pattern or an equivalent transactionally reliable mechanism.
   824→
   825→Do not do:
   826→
   827→```text
   828→DB commit
   829→→ hope event send succeeds
   830→```
   831→
   832→Preferred:
   833→
   834→```text
   835→DB transaction
   836→  ├─ business state
   837→  └─ outbox event
   838→       ↓
   839→commit
   840→       ↓
   841→outbox dispatcher
   842→       ↓
   843→event transport
   844→       ↓
   845→consumer
   846→```
   847→
   848→Consumers MUST be idempotent.
   849→
   850→The actual broker technology is an implementation choice recorded in an ADR; domain contracts do not depend on a specific broker.
   851→
   852→---
   853→
   854→# 24. GATEWAY CONTROL CONTRACT
   855→
   856→The policy/control layer MUST express intent, not CLI syntax.
   857→
   858→Example logical request:
   859→
   860→```json
   861→{
   862→  "session_id": "sess_123",
   863→  "policy_version": 42,
   864→  "access": {
   865→    "ipv4": "203.0.113.10",
   866→    "vrf": "internet",
   867→    "vlan": 120
   868→  },
   869→  "qos": {
   870→    "profile": "plan-100m"
   871→  },
   872→  "acl": {
   873→    "profile": "subscriber-default"
   874→  },
   875→  "nat": {
   876→    "profile": "cgnat-default"
   877→  }
   878→}
   879→```
   880→
   881→The VPP Adapter translates this to VPP object operations.
   882→
   883→The API/UI MUST NOT contain VPP-specific command-building logic.
   884→
   885→---
   886→
   887→# 25. VPP OPERATION RESULT
   888→
   889→Every gateway mutation returns a structured result internally:
   890→
   891→```text
   892→command_id
   893→session_id / object_id
   894→requested_version
   895→applied_version
   896→status
   897→retries
   898→error_code
   899→error_message
   900→vpp_context
   901→applied_at
   902→```
   903→
   904→A control-plane success is not accepted until the requested VPP object state has reached the required acknowledgement state.
   905→
   906→---
   907→
   908→# 26. RECONCILIATION CONTRACT
   909→
   910→The Session Engine maintains the desired state; the VPP Adapter observes and reconciles actual state.
   911→
   912→State comparison:
   913→
   914→```text
   915→Desired Session State
   916→       vs
   917→Actual Dataplane State
   918→```
   919→
   920→Outcomes:
   921→
   922→- `IN_SYNC`
   923→- `MISSING_ACTUAL`
   924→- `STALE_ACTUAL`
   925→- `MISMATCHED_POLICY`
   926→- `UNKNOWN_ACTUAL`
   927→- `RECONCILE_REQUIRED`
   928→
   929→Reconciliation is idempotent.
   930→

   971→# 28. AUTHORIZATION ENFORCEMENT
   972→
   973→Every API operation maps to a permission such as:
   974→
   975→```text
   976→subscriber.read
   977→subscriber.write
   978→billing.invoice.generate
   979→billing.payment.refund
   980→session.read
   981→session.disconnect
   982→policy.read
   983→policy.write
   984→network.device.manage
   985→audit.read
   986→admin.role.manage
   987→```
   988→

   990→
   991→UI visibility is not authorization.
   992→
   993→Sensitive commands require explicit permissions and produce audit events.

   997→# 29. RATE LIMITING / RESOURCE PROTECTION
   998→
   999→Apply bounded controls by class:
  1000→
  1001→| Interface | Control |
  1002→|---|---|
  1003→| Login | IP/user/device throttling |
  1004→| Public APIs | tenant/user/IP rate limits |
  1005→| Search | minimum query constraints |
  1006→| Export | concurrency/job limits |
  1007→| Diagnostics | concurrency + cooldown |
  1008→| Device polling | scheduler bounds |
  1009→| Gateway commands | bounded queue + dedupe |
  1010→| Batch provisioning | job concurrency |
  1011→| AI | token/cost/request budgets |
  1012→| Webhooks | per-provider retry limits |
  1013→
  1014→Do not let a UI refresh create an unbounded downstream polling storm.

  1128→# 36. NON-NEGOTIABLE RULES
  1129→
  1130→1. API code must not become packet forwarding code.
  1131→2. UI code must not contain gateway enforcement logic.
  1132→3. Database writes do not imply dataplane success.
  1133→4. Access-Accept does not imply session `ACTIVE`.
  1134→5. Events are contracts, not ad-hoc strings.
  1135→6. Consumers must be idempotent.
  1136→7. Large work must be bounded and observable.
  1137→8. Permissions are enforced server-side.
  1138→9. Financial commands must be auditable and retry-safe.
  1139→10. No endpoint may create unbounded load on PostgreSQL, VPP, or external providers.
