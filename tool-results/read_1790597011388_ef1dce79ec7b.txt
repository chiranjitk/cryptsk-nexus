    39→# 2. Fundamental Architecture Decision
    40→
    41→Do NOT build the new system as:
    42→
    43→``` text
    44→RADIUS
    45→   ↓
    46→shell script
    47→   ↓
    48→nftables
    49→   ↓
    50→tc
    51→   ↓
    52→packet enforcement
    53→```
    54→
    55→Do NOT make FreeRADIUS responsible for maintaining the complete live
    56→subscriber state.
    57→
    58→The new architecture is:
    59→
    60→``` text
    61→                         MANAGEMENT PLANE
    62→                               │
    63→                         REST / gRPC API
    64→                               │
    65→                               ▼
    66→                       ┌───────────────┐
    67→                       │ Policy Engine │
    68→                       └───────┬───────┘
    69→                               │
    70→              ┌────────────────┼────────────────┐
    71→              │                │                │
    72→              ▼                ▼                ▼
    73→        AAA Service      Session Engine    IPAM/Pool Engine
    74→              │                │                │
    75→              ▼                ▼                ▼
    76→        FreeRADIUS        Live Sessions      PostgreSQL
    77→              │                │
    78→              │                ▼
    79→              │          VPP Adapter
    80→              │                │
    81→              └────────────────┤
    82→                               ▼
    83→                         VPP / DPDK
    84→                               │
    85→                         Physical NIC
    86→                               │
    87→                         Subscriber traffic
    88→```
    89→
    90→The responsibilities MUST remain separated.

   132→# 4. Session Engine
   133→
   134→The Session Engine is the core new component.
   135→
   136→It owns the authoritative live subscriber/session state.
   137→
   138→Example:
   139→
   140→``` text
   141→Session ID
   142→Username
   143→Subscriber ID
   144→NAS ID
   145→Access protocol
   146→IPv4
   147→IPv6
   148→MAC
   149→VLAN
   150→Interface
   151→VRF
   152→Authentication time
   153→Last accounting update
   154→Session state
   155→Policy ID
   156→Bandwidth profile
   157→QoS profile
   158→ACL profile
   159→NAT profile
   160→IP pool
   161→Accounting state
   162→Data counters
   163→Packet counters
   164→Idle timeout
   165→Session timeout
   166→Device information
   167→```
   168→
   169→The Session Engine MUST be independent from FreeRADIUS.
   170→
   171→------------------------------------------------------------------------
   172→
   173→# 5. Why Session Engine Must Be Separate
   174→
   175→RADIUS is a request/response AAA protocol.
   176→
   177→A subscriber session may remain online for:
   178→
   179→-   minutes
   180→-   hours
   181→-   days
   182→-   weeks
   183→
   184→The RADIUS Access-Accept is only the authentication decision.
   185→
   186→Therefore:
   187→
   188→``` text
   189→RADIUS request
   190→      ↓
   191→Authentication decision
   192→      ↓
   193→Access-Accept
   194→      ↓
   195→Session Engine creates live session
   196→      ↓
   197→VPP enforces policy
   198→```
   199→
   200→The session continues even when there is no RADIUS packet.
   201→
   202→------------------------------------------------------------------------

   254→# 7. Session Lifecycle
   255→
   256→## 7.1 Login
   257→
   258→``` text
   259→Subscriber
   260→    ↓
   261→NAS
   262→    ↓
   263→RADIUS Access-Request
   264→    ↓
   265→FreeRADIUS
   266→    ↓
   267→Authentication
   268→    ↓
   269→Authorization
   270→    ↓
   271→Access-Accept
   272→    ↓
   273→Session Engine
   274→    ↓
   275→Create session
   276→    ↓
   277→Allocate IP
   278→    ↓
   279→Resolve subscriber policy
   280→    ↓
   281→Generate dataplane policy
   282→    ↓
   283→VPP Adapter
   284→    ↓
   285→VPP
   286→    ↓
   287→Subscriber becomes ACTIVE
   288→```
   289→
   290→------------------------------------------------------------------------
   291→
   292→# 8. Login Must Be Transactional
   293→
   294→Do NOT mark the subscriber ACTIVE before dataplane programming succeeds.
   295→
   296→Correct sequence:
   297→
   298→``` text
   299→1. Authenticate
   300→2. Authorize
   301→3. Allocate IP
   302→4. Create session
   303→5. Program VPP
   304→6. Verify VPP programming
   305→7. Mark ACTIVE
   306→8. Start accounting
   307→```
   308→
   309→If VPP programming fails:
   310→
   311→``` text
   312→Authentication successful
   313→        ↓
   314→VPP programming failed
   315→        ↓
   316→Session NOT ACTIVE
   317→        ↓
   318→Return controlled failure
   319→```
   320→
   321→Do not create "ghost sessions".
   322→
   323→------------------------------------------------------------------------
   324→
   325→# 9. Logout
   326→
   327→Logout may originate from:
   328→
   329→-   NAS Accounting-Stop
   330→-   RADIUS Disconnect
   331→-   CoA
   332→-   session timeout
   333→-   idle timeout
   334→-   administrative disconnect
   335→-   duplicate login policy
   336→-   IP conflict
   337→-   NAS failure recovery
   338→-   system policy
   339→-   subscriber suspension
   340→-   account expiry
   341→
   342→Flow:
   343→
   344→``` text
   345→Logout Event
   346→     ↓
   347→Session Engine
   348→     ↓
   349→Locate session
   350→     ↓
   351→Mark DISCONNECTING
   352→     ↓
   353→Remove VPP policy/state
   354→     ↓
   355→Release IP
   356→     ↓
   357→Close accounting state
   358→     ↓
   359→Persist final session record
   360→     ↓
   361→Mark DISCONNECTED
   362→```
   363→
   364→Operations MUST be idempotent.
   365→
   366→Calling logout twice must not corrupt state.
   367→
   368→------------------------------------------------------------------------
   369→
   370→# 10. FreeRADIUS ↔ Session Engine
   371→
   372→Do not tightly couple FreeRADIUS configuration to application internals.
   373→
   374→Use an adapter:
   375→
   376→``` text
   377→FreeRADIUS
   378→     │
   379→     │ RADIUS events
   380→     ▼
   381→AAA Adapter
   382→     │
   383→     ▼
   384→Session Engine API
   385→```
   386→
   387→The adapter can use:
   388→
   389→-   local UNIX socket
   390→-   localhost gRPC
   391→-   REST for management operations
   392→-   message queue for asynchronous events
   393→
   394→For high-frequency internal events, prefer:
   395→
   396→``` text
   397→gRPC / Unix socket / internal message bus
   398→```
   399→
   400→over REST.
   401→
   402→REST should primarily be the management interface.
   403→

   486→# 13. PostgreSQL Responsibilities
   487→
   488→PostgreSQL is the durable source of configuration, identity,
   489→accounting-history, audit, and recovery metadata.
   490→
   491→It is NOT the authoritative real-time store for packet-path state or the
   492→sole source of truth for live session ownership.
   493→
   494→Live session state is authoritative in the Session Engine; PostgreSQL
   495→provides durable configuration/history and recovery persistence.
   496→
   497→Use PostgreSQL for:
   498→
   499→-   subscribers
   500→-   credentials
   501→-   subscriber profiles
   502→-   service plans
   503→-   policies
   504→-   NAS definitions
   505→-   IP pools
   506→-   VLANs
   507→-   gateway configuration
   508→-   accounting history
   509→-   session history
   510→-   audit logs
   511→-   administrator data
   512→-   configuration
   513→-   billing information
   514→
   515→Do NOT use PostgreSQL as the packet-path state store.
   516→
   517→------------------------------------------------------------------------
   518→
   519→# 14. Live Session Storage
   520→
   521→Live sessions should primarily exist in memory inside the Session
   522→Engine.
   523→
   524→Example:
   525→
   526→``` text
   527→Session Engine
   528→      │
   529→      ├── HashMap / concurrent map
   530→      ├── IP → Session index
   531→      ├── MAC → Session index
   532→      ├── Username → Session index
   533→      ├── Session-ID → Session index
   534→      └── NAS → session index
   535→```
   536→
   537→Optional Redis can be used for:
   538→
   539→-   HA coordination
   540→-   distributed locks
   541→-   temporary state
   542→-   event distribution
   543→-   shared cache
   544→
   545→But Redis should not automatically become the packet-path database.
   546→

   549→# 15. 100,000 Session Architectural Target
   550→
   551→The platform MUST be architected for 100,000 concurrent sessions from
   552→day one.
   553→
   554→The first production/certification profile may be 50,000 sessions, but
   555→the software architecture must not contain a 50k-specific ceiling.
   556→
   557→100,000 concurrent sessions is not itself a difficult memory problem.
   558→The real scalability dimensions are:
   559→
   560→The real scalability dimensions are:
   561→
   562→``` text
   563→Concurrent sessions
   564→+
   565→Authentication requests/sec
   566→+
   567→Accounting packets/sec
   568→+
   569→CoA/sec
   570→+
   571→Disconnect/sec
   572→+
   573→New sessions/sec
   574→+
   575→Database writes/sec
   576→+
   577→VPP policy operations/sec
   578→+
   579→NAT flows
   580→+
   581→Packets/sec
   582→+
   583→Bandwidth
   584→```
   585→
   586→The architecture MUST therefore define capacity independently for each
   587→dimension.
   588→
   589→------------------------------------------------------------------------
   590→
   591→# 16. Example Accounting Load
   592→
   593→For 100,000 active sessions:
   594→
   595→With 5-minute interim updates:
   596→
   597→``` text
   598→100,000 / 300
   599→≈ 333 accounting updates/sec
   600→```
   601→
   602→With 1-minute interim updates:
   603→
   604→``` text
   605→100,000 / 60
   606→≈ 1,667 accounting updates/sec
   607→```
   608→
   609→Therefore, do NOT blindly configure 60-second SQL accounting updates for
   610→every deployment.
   611→
   612→Make the accounting interval configurable.
   613→
   614→Recommended defaults:
   615→
   616→``` text
   617→Interim update:
   618→300 seconds
   619→
   620→High-accuracy mode:
   621→60–120 seconds
   622→
   623→Low-load mode:
   624→300–600 seconds
   625→```
   626→
   627→The final choice must depend on billing/audit requirements.
   628→
   629→------------------------------------------------------------------------
   630→
   631→# 17. Accounting Architecture
   632→
   633→Do not force every Accounting-Interim packet directly into a large
   634→PostgreSQL transaction if unnecessary.
   635→
   636→Recommended:
   637→
   638→``` text
   639→NAS
   640→ ↓
   641→FreeRADIUS
   642→ ↓
   643→Accounting Processor
   644→ ↓
   645→Event Queue
   646→ ↓
   647→Accounting Writer
   648→ ↓
   649→PostgreSQL
   650→```
   651→
   652→For high-load installations:
   653→
   654→``` text
   655→RADIUS
   656→ ↓
   657→fast acknowledgement
   658→ ↓
   659→buffer/event queue
   660→ ↓
   661→batch DB writer
   662→```
   663→
   664→FreeRADIUS documentation explicitly describes buffered accounting as a
   665→way to decouple busy RADIUS processing from slower SQL writes.
   666→
   667→------------------------------------------------------------------------
   668→
   669→# 18. Accounting Tables
   670→
   671→Do not allow `radacct` to grow indefinitely as one unpartitioned table.
   672→
   673→Use time partitioning.
   674→
   675→Example:
   676→
   677→``` text
   678→radacct
   679→ ├── 2026_09
   680→ ├── 2026_10
   681→ ├── 2026_11
   682→ └── ...
   683→```
   684→
   685→Indexes should be designed around actual queries.
   686→
   687→Important lookup dimensions:
   688→
   689→``` text
   690→session_id
   691→acct_session_id
   692→username
   693→subscriber_id
   694→nas_id
   695→framed_ip
   696→mac
   697→start_time
   698→stop_time
   699→```
   700→
   701→Do not create unnecessary indexes because every additional index
   702→increases write cost.

   707→
   708→Authentication can use multiple levels:
   709→
   710→``` text
   711→L1:
   712→Session Engine / local cache
   713→
   714→L2:

   743→# 20. FreeRADIUS Threading
   744→
   745→FreeRADIUS uses a thread pool.
   746→
   747→The configuration must be tuned based on:
   748→
   749→-   CPU cores
   750→-   request rate
   751→-   authentication backend latency
   752→-   SQL latency
   753→-   LDAP latency
   754→-   EAP workload
   755→-   accounting load
   756→
   757→Do not simply configure hundreds of threads because there are 100,000
   758→sessions.
   759→
   760→100,000 sessions ≠ 100,000 FreeRADIUS threads.
   761→
   762→Thread count must be derived from request rate, backend latency,
   763→protocol mix, CPU, and measured queueing behavior.
   764→
   765→A session is not a FreeRADIUS worker.
   766→
   767→------------------------------------------------------------------------

  1516→# 43. High Availability
  1517→
  1518→HA MUST be separated into clearly defined service levels:
  1519→
  1520→1.  Control-plane HA
  1521→2.  Session/state HA
  1522→3.  Stateful dataplane/NAT HA
  1523→
  1524→The product must not advertise "stateful HA" merely because PostgreSQL
  1525→and management services are replicated.
  1526→
  1527→For enterprise deployments:
  1528→
  1529→``` text
  1530→                 ┌──────────────┐
  1531→                 │ PostgreSQL HA│
  1532→                 └──────┬───────┘
  1533→                        │
  1534→             ┌──────────┴──────────┐
  1535→             │                     │
  1536→       Gateway Node A        Gateway Node B
  1537→             │                     │
  1538→        VPP + Session          VPP + Session
  1539→             │                     │
  1540→             └──────────┬──────────┘
  1541→                        │
  1542→                     Network
  1543→```
  1544→
  1545→HA design should distinguish:
  1546→
  1547→### Control-plane HA
  1548→
  1549→Easy to replicate:
  1550→
  1551→-   configuration
  1552→-   policies
  1553→-   subscribers
  1554→-   NAS
  1555→-   accounting
  1556→
  1557→### Dataplane/session HA
  1558→
  1559→Much harder:
  1560→
  1561→-   active NAT state
  1562→-   active flows
  1563→-   subscriber state
  1564→-   packet counters
  1565→
  1566→Do not claim stateful HA until actual state replication is implemented
  1567→and tested.
  1568→

  1623→# 46. IPAM
  1624→
  1625→Create a dedicated IPAM module.
  1626→
  1627→For 100k-scale operation, IPAM MUST use an in-memory allocation
  1628→structure plus durable recovery state. PostgreSQL transactions may be
  1629→used for authoritative persistence and conflict prevention, but IP
  1630→allocation must not require a full SQL round-trip for every subscriber
  1631→when the system is under high login churn.
  1632→
  1633→Responsibilities:
  1634→
  1635→``` text
  1636→Pool creation
  1637→Pool deletion
  1638→Pool status
  1639→Free IP count
  1640→Allocated IP count
  1641→Reservation
  1642→Static IP
  1643→Dynamic IP
  1644→Lease
  1645→Expiration
  1646→Subscriber mapping
  1647→```
  1648→
  1649→For very high-concurrency allocation, use transactional allocation.
  1650→
  1651→Avoid:
  1652→
  1653→``` text
  1654→SELECT free IP
  1655→↓
  1656→application waits
  1657→↓
  1658→UPDATE IP
  1659→```
  1660→
  1661→because concurrent workers can collide.
  1662→
  1663→Use atomic/transactional allocation.
  1664→
  1665→------------------------------------------------------------------------
  1666→
  1667→# 47. IP Pool Model
  1668→
  1669→``` text
  1670→IP Pool
  1671→ ├── pool_id
  1672→ ├── name
  1673→ ├── network
  1674→ ├── gateway
  1675→ ├── VLAN
  1676→ ├── VRF
  1677→ ├── allocation mode
  1678→ ├── static/dynamic
  1679→ └── address range
  1680→```
  1681→
  1682→Allocation:
  1683→
  1684→``` text
  1685→subscriber
  1686→    ↓
  1687→service profile
  1688→    ↓
  1689→IP pool
  1690→    ↓
  1691→IPAM
  1692→    ↓
  1693→IP address
  1694→```
  1695→
  1696→------------------------------------------------------------------------
  1697→
  1698→# 48. IPAM Performance
  1699→
  1700→If SQL-based IP allocation is used, use proper transactional allocation
  1701→and avoid lock contention.
  1702→
  1703→The FreeRADIUS project specifically documents
  1704→`SELECT ... FOR UPDATE SKIP LOCKED` and stored procedures as mechanisms
  1705→for high-concurrency SQL IP allocation.
  1706→
  1707→For a very high-throughput gateway, however, the preferred architecture
  1708→is:
  1709→
  1710→``` text
  1711→IPAM service
  1712→     ↓
  1713→in-memory free-address structures
  1714→     ↓
  1715→durable state asynchronously persisted
  1716→```
  1717→
  1718→while retaining transactional recovery semantics.
