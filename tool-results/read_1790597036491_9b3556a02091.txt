     1→# CRYPTSK NEXUS — DATABASE & DATA MODEL SPECIFICATION
     2→## Canonical domain model, PostgreSQL design, live-state boundary, accounting, audit, retention, and migration rules
     3→
     4→**Status:** LOCKED DATABASE / DATA MODEL BASELINE
     5→**Authority:** Subordinate to `00_MASTER_PRODUCT_ARCHITECTURE.md`; functionally grounded in `04_PRODUCT_FEATURE_CATALOGUE.md` and the gateway/session architecture.

     7→---
     8→
     9→# 1. PURPOSE
    10→
    11→This document converts the functional data inventory into a canonical production data architecture.
    12→
    13→The database design MUST support:
    14→
    15→- full OSS/BSS functionality;
    16→- AAA/accounting integration;
    17→- 100,000 concurrent sessions;
    18→- fast live-session lookup without using PostgreSQL as the packet path;
    19→- durable historical records;
    20→- financial correctness;
    21→- auditability;
    22→- multi-tenant/organizational boundaries where enabled;
    23→- high-volume accounting and telemetry ingestion;
    24→- migrations from the existing feature-sheet data model;
    25→- future module expansion without schema chaos.
    26→

    29→# 2. SOURCE INVENTORY RECONCILIATION — MANDATORY GATE
    30→
    31→The source feature sheet states:
    32→
    33→- 204 Prisma models
    34→- 90 enums
    35→
    36→The grouped model names in the source inventory contain **204 named model entries**, so the model count itself reconciles. Several inline group labels in the source sheet are inaccurate; the corrected counts are recorded in `04_PRODUCT_FEATURE_CATALOGUE.md`.
    37→
    38→The source feature sheet reports **90 enums**, but the named enum list in the same inventory contains **99 unique enum names**. This is the remaining source-enumeration discrepancy. The new system MUST NOT invent or delete enums merely to force the historical count to match.
    39→
    40→Before schema freeze, create a reconciliation register for the enum inventory and any legacy model merge/split decisions:
    41→
    42→```text
    43→source model/enum
    44→→ canonical entity/enum
    45→→ retained / merged / split / deprecated
    46→→ domain owner
    47→→ migration strategy
    48→→ references
    49→```
    50→
    51→The authoritative metric for the CRYPTSK Nexus is the canonical schema and approved migration register, not a historical headline count.
    52→
    53→The source enums are a functional reference; each must be classified as:
    54→
    55→- retained enum;
    56→- normalized enum;
    57→- status state machine;
    58→- free-form/extensible reference where appropriate;
    59→- deprecated legacy enum.

    63→# 3. DATABASE AUTHORITY
    64→
    65→Production system of record:
    66→
    67→```text
    68→PostgreSQL
    69→```
    70→
    71→Development may use lightweight adapters only where they preserve domain behavior, but production semantics must be PostgreSQL-first.
    72→
    73→PostgreSQL stores durable business/configuration/history state.
    74→
    75→It MUST NOT be used as the per-packet policy lookup mechanism.
    76→

    79→# 4. DATA-STATE CLASSIFICATION
    80→
    81→Every data object MUST be classified into one of these classes.
    82→
    83→## 4.1 Configuration state
    84→
    85→Examples:
    86→
    87→- plan
    88→- policy definition
    89→- NAS configuration
    90→- firewall rule
    91→- IP pool
    92→- DNS configuration
    93→- billing settings
    94→- integration settings
    95→
    96→Characteristics:
    97→
    98→- durable;
    99→- versioned where necessary;
   100→- auditable;
   101→- relatively low update frequency.
   102→
   103→## 4.2 Transactional state
   104→
   105→Examples:
   106→
   107→- subscriber
   108→- service
   109→- invoice
   110→- payment
   111→- complaint
   112→- installation
   113→- inventory transaction.
   114→
   115→Characteristics:
   116→
   117→- ACID transaction semantics;
   118→- business constraints;
   119→- audit trail as required.
   120→
   121→## 4.3 Runtime/ephemeral state
   122→
   123→Examples:
   124→
   125→- gateway worker queues;
   126→- current VPP object handles;
   127→- in-memory session index;
   128→- current connection state;
   129→- transient control-plane leases.
   130→
   131→These MUST NOT depend on PostgreSQL for every packet or high-frequency mutation.
   132→
   133→## 4.4 Historical state
   134→
   135→Examples:
   136→
   137→- session history;
   138→- accounting samples;
   139→- NAT logs;
   140→- authentication logs;
   141→- audit logs;
   142→- network telemetry;
   143→- notification delivery history.
   144→
   145→Designed for append-heavy ingestion and analytical access.

   158→6. Session / Accounting
   159→7. Network / IPAM
   160→8. Gateway / Security / QoS
   161→9. Billing / Finance
   162→10. Operations / Support
   163→11. Inventory / Assets
   164→12. Monitoring / Alerts
   165→13. Integrations / Notifications
   166→14. Reporting / Analytics
   167→15. AI / Intelligence
   168→
   169→A model belongs to one primary domain owner even when referenced by many modules.

   173→# 6. TENANCY / ORGANIZATION MODEL
   174→
   175→Where multi-tenant operation is enabled, domain records requiring isolation MUST carry an explicit tenant/organization boundary.
   176→
   177→Canonical pattern:
   178→
   179→```text
   180→Tenant
   181→ ├─ Organization
   182→ │   ├─ Business Unit / Site / Scope (when enabled)
   183→ │   ├─ Users / Delegated Administrators
   184→ │   ├─ Customers
   185→ │   ├─ Subscribers / Service Consumers
   186→ │   ├─ Services
   187→ │   ├─ Plans
   188→ │   ├─ Network
   189→ │   └─ Billing
   190→```
   191→
   192→Do not infer tenant identity only from the current URL or UI route.
   193→
   194→Authorization scope is enforced in the application/service layer, with database constraints/indexes supporting safe filtering.
   195→
   196→---
   197→
   198→# 7. IDENTITY MODEL
   199→
   200→Use stable opaque identifiers for platform entities.
   201→
   202→Recommended logical format:
   203→
   204→```text
   205→sub_...
   206→svc_...
   207→plan_...
   208→sess_...
   209→nas_...
   210→inv_...
   211→pay_...
   212→policy_...
   213→op_...
   214→```
   215→
   216→The exact physical type may be UUID/UUID-like or another approved stable identifier. The API MUST NOT expose database sequence assumptions.
   217→
   218→External IDs are separate from internal IDs when integration systems require their own identifier.
   219→
   220→---
   221→
   222→# 8. CUSTOMER / SUBSCRIBER / SERVICE MODEL
   223→
   224→Do not collapse Customer, Subscriber/Service Consumer, and Service into one record. Subscriber is a vertical/network terminology choice; the universal domain remains Customer/Account/Service.
   225→
   226→```text
   227→Customer / Organization
   228→        │
   229→        └── Subscriber
   230→               │
   231→               ├── Service / Subscription
   232→               │       ├── Plan
   233→               │       └── Access Profile
   234→               │
   235→               └── Device / Identity associations
   236→```
   237→
   238→A subscriber may have multiple services over time.
   239→
   240→A service has its own lifecycle:
   241→
   242→```text
   243→DRAFT → PROVISIONING → ACTIVE → SUSPENDED → TERMINATING → TERMINATED
   244→```
   245→
   246→Historical state must be reconstructable from durable records.
   247→
   248→---
   249→
   250→# 9. PLAN / PRODUCT / POLICY MODEL
   251→
   252→Business plan and gateway enforcement policy are related but distinct.
   253→
   254→```text
   255→Product
   256→  └─ Plan
   257→      ├─ Pricing
   258→      ├─ Service rules
   259→      └─ Network Policy Reference
   260→             ├─ QoS
   261→             ├─ ACL
   262→             ├─ NAT
   263→             ├─ DNS
   264→             └─ Application/DPI
   265→```
   266→
   267→A plan may be edited, but already-issued policy versions remain identifiable.
   268→
   269→Policy compilation creates a versioned representation suitable for runtime enforcement.
   270→
   271→---
   272→
   273→# 10. POLICY VERSIONING
   274→
   275→Every runtime-relevant policy has:
   276→
   277→```text
   278→policy_id
   279→policy_version
   280→status
   281→created_at
   282→created_by
   283→compiled_at
   284→compiled_hash
   285→effective_from
   286→effective_to
   287→```
   288→
   289→A compiled policy has a deterministic fingerprint.
   290→
   291→The gateway must be able to answer:
   292→
   293→```text
   294→Which policy version was applied to this session at time T?
   295→```
   296→
   297→This is essential for support, audit, debugging, and billing disputes.
   298→

   324→# 12. RADIUS COMPATIBILITY BOUNDARY
   325→
   326→The canonical ownership is:
   327→
   328→```text
   329→Cryptsk Subscriber/Service
   330→       ↓
   331→AAA projection / RADIUS authorization data
   332→       ↓
   333→FreeRADIUS
   334→```
   335→
   336→The projection MUST be reconcilable.
   337→
   338→Maintain a provisioning/reconciliation record showing:
   339→
   340→- desired AAA state;
   341→- last successful projection;
   342→- current projection status;
   343→- error information;
   344→- source entity version.
   345→
   346→Do not rely on blind table synchronization without state tracking.
   347→

   350→# 13. SESSION DATA MODEL
   351→
   352→A session record logically contains:
   353→
   354→```text
   355→session_id
   356→subscriber_id
   357→service_id
   358→username
   359→nas_id
   360→access_type
   361→mac_address
   362→vlan_id
   363→vrf_id
   364→ipv4_address
   365→ipv6_prefix
   366→policy_id
   367→policy_version
   368→bandwidth_profile
   369→acl_profile
   370→nat_profile
   371→started_at
   372→last_seen_at
   373→last_accounting_at
   374→state
   375→termination_reason
   376→authentication_source
   377→session_epoch
   378→```
   379→
   380→Runtime counters may be sampled into durable usage records, but live high-frequency counters remain owned by the Session Engine/gateway telemetry system.
   381→
   382→---
   383→
   384→# 14. SESSION HISTORY
   385→
   386→Session history is durable and queryable.
   387→
   388→At minimum capture:
   389→
   390→- start;
   391→- authentication context;
   392→- service/plan/policy;
   393→- IP/MAC/NAS;
   394→- accounting samples;
   395→- policy changes;
   396→- CoA/disconnect actions;
   397→- stop reason;
   398→- final counters;
   399→- reconciliation status.
   400→
   401→History is not the same object as the live session index.
   402→
   403→---
   404→
   405→# 15. ACCOUNTING MODEL
   406→
   407→Use append-oriented accounting ingestion where practical.
   408→
   409→A normalized accounting event should contain:
   410→
   411→```text
   412→event_id
   413→source
   414→nas_id
   415→external_session_id
   416→session_id if resolved
   417→username
   418→packet_type
   419→received_at
   420→nas_event_time
   421→input_octets
   422→output_octets
   423→session_time
   424→raw/reference metadata
   425→dedupe_key
   426→```
   427→
   428→Normalization must account for RADIUS counter semantics and source resets.
   429→
   430→The system must preserve enough information to explain how a final usage total was produced.
   431→
   432→---
   433→
   434→# 16. HIGH-VOLUME SESSION / ACCOUNTING TABLES
   435→
   436→Tables expected to grow quickly should be designed separately from small configuration tables.
   437→
   438→Examples:
   439→
   440→- accounting_events;
   441→- session_usage_samples;
   442→- authentication_events;
   443→- session_events;
   444→- NAT logs;
   445→- syslog messages;
   446→- telemetry samples;
   447→- audit events.
   448→
   449→Use appropriate partitioning and retention when measured volume justifies it.
   450→
   451→Do not partition every table preemptively.
   452→
   453→---
   454→
   455→# 17. INDEX PRINCIPLES
   456→
   457→Critical active-session lookup keys include:
   458→
   459→```text
   460→session_id
   461→subscriber_id + state
   462→username + state
   463→ip_address + state
   464→mac_address + state
   465→nas_id + state
   466→external_session_id + nas_id
   467→```
   468→
   469→Common business indexes include:
   470→
   471→- tenant/org + status;
   472→- subscriber + service status;
   473→- invoice + status + due date;
   474→- payment + created_at;
   475→- device + status;
   476→- policy + version/status;
   477→- alert + status + severity;
   478→- audit + actor + occurred_at;
   479→- operation + status.
   480→
   481→Indexes must be validated using actual query plans.
   482→
   483→---
   484→
   485→# 18. CONSTRAINTS
   486→
   487→Use the database to enforce durable invariants such as:
   488→
   489→- unique external identifiers within scope;
   490→- nonnegative monetary values where applicable;
   491→- valid foreign-key ownership;
   492→- valid status transitions through application/domain logic;
   493→- unique active assignment where the business rule requires it;
   494→- immutable transaction identifiers.
   495→
   496→Application validation remains necessary; database constraints are the final integrity boundary.
   497→
   498→---
   499→
   500→# 19. MONEY / FINANCIAL DATA
   501→
   502→Never use floating-point storage for currency amounts.
   503→
   504→Use:
   505→
   506→- fixed-precision numeric/decimal;
   507→- explicit currency code;
   508→- explicit tax/discount components;
   509→- deterministic rounding rules;
   510→- immutable transaction IDs;
   511→- audit trail.
   512→
   513→Financial documents should preserve the calculation inputs required to reproduce the total.
   514→

   516→
   517→# 20. INVOICE MODEL
   518→
   519→Invoice should separate:
   520→
   521→- header;
   522→- billing period;
   523→- line items;
   524→- taxes;
   525→- discounts;
   526→- adjustments;
   527→- payments/allocations;
   528→- credit notes;
   529→- balance;
   530→- status history.
   531→
   532→Do not derive historical invoice totals purely from today's plan configuration.

   537→
   538→Payment must capture:
   539→
   540→- payment ID;
   541→- external gateway transaction/reference;
   542→- mode/provider;
   543→- amount/currency;
   544→- received timestamp;
   545→- allocation to invoices;
   546→- status;
   547→- verification state;
   548→- refund history;
   549→- idempotency key/reference;
   550→- reconciliation state.

   555→
   556→# 21A. PREPAID / TOP-UP / VOUCHER MODEL
   557→
   558→Where prepaid commerce is enabled, maintain distinct durable records for:
   559→
   560→- top-up product;
   561→- prepaid wallet/balance ledger;
   562→- voucher/PIN definition;
   563→- voucher batch;
   564→- voucher issuance;
   565→- redemption;
   566→- expiry;
   567→- reversal/adjustment.
   568→
   569→A voucher/PIN is not the same thing as a package definition or a payment transaction.
   570→
   571→# 21B. SERVICE CONTRACT / AMC MODEL
   572→
   573→Where managed-service contracts are enabled, maintain:
   574→
   575→- contract;
   576→- customer/service links;
   577→- entitlement tier;
   578→- covered assets/services;
   579→- SLA commitments;
   580→- effective/expiry dates;
   581→- renewal state;
   582→- support coverage;
   583→- audit history.
   584→
   585→# 22. INVENTORY / ASSET MODEL
   586→
   587→Equipment, stock, warehouse, purchase order, return, repair, and inspection are separate concepts.
   588→
   589→Inventory mutation should be represented as auditable transactions rather than overwriting history.
   590→
   591→Example:
   592→
   593→```text
   594→Purchase
   595→ → Receive
   596→ → Stock
   597→ → Assign
   598→ → Install
   599→ → Repair
   600→ → Return / Dispose
   601→```

   663→# 26. MONITORING / ALERT DATA
   664→
   665→Monitoring objects:
   666→
   667→- metric definitions;
   668→- threshold/rule;
   669→- alert;
   670→- alert state history;
   671→- suppression window;
   672→- comment/acknowledgement;
   673→- notification delivery.
   674→
   675→Do not use transactional tables as a high-frequency time-series database simply because they already exist.

   680→
   681→# 26A. WEB BROWSING / HTTP LOG DATA
   682→
   683→Where enabled, store a queryable, retention-controlled web browsing log with fields such as:
   684→
   685→```text
   686→log_id
   687→timestamp
   688→subscriber/service/session reference when resolved
   689→source IP / port when available
   690→destination IP / port when available
   691→host/domain metadata when available
   692→HTTP method/status for visible HTTP traffic
   693→bytes when available
   694→gateway/node reference
   695→correlation/session identifiers
   696→retention class
   697→```
   698→
   699→Do not represent standard HTTPS traffic as full URL/path/payload visibility without an approved inspection/decryption architecture.
   700→
   701→# 27. AUDIT MODEL
   702→
   703→Audit records are immutable.
   704→
   705→Capture:
   706→
   707→```text
   708→actor
   709→actor_type
   710→tenant/scope
   711→action
   712→entity_type
   713→entity_id
   714→before_summary
   715→change_summary
   716→reason if required
   717→request_id
   718→correlation_id
   719→source
   720→occurred_at
   721→result
   722→```
   723→
   724→Secrets and sensitive fields must be redacted.
   725→
   726→Audit data must not be silently deleted because an application record was deleted.
   727→

   735→
   736→```text

   739→event_version

   862→# 34. LIVE SESSION STORAGE BOUNDARY
   863→
   864→Authoritative live state:
   865→
   866→```text
   867→Session Engine
   868→```
   869→
   870→Durable state/history:
   871→
   872→```text
   873→PostgreSQL
   874→```
   875→
   876→Optional cache/coordination:
   877→
   878→```text
   879→Redis, only when justified
   880→```
   881→
   882→Redis MUST NOT silently become the only source of live truth.
   883→
   884→PostgreSQL MUST NOT become a per-packet state store.
   885→
   886→---
   887→
   888→# 35. SESSION SNAPSHOT / RECOVERY
   889→
   890→Session Engine MUST periodically or transactionally preserve enough durable information to reconstruct required live intent after process restart.
   891→
   892→The recovery process is:
   893→
   894→```text
   895→Durable desired session state
   896→        ↓
   897→Session Engine restore
   898→        ↓
   899→VPP actual-state inspection
   900→        ↓
   901→Reconciliation
   902→        ↓
   903→Recovered ACTIVE / terminated / manual-review state
   904→```
   905→
   906→The design must tolerate:
   907→
   908→- process restart;
   909→- node restart;
   910→- VPP restart;
   911→- network interruption;
   912→- delayed accounting;
   913→- duplicated events.
   914→
   915→---
   916→
   917→# 36. RETENTION CLASSES
   918→
   919→Every high-volume table must have a documented retention class.
   920→
   921→Example classes:
   922→
   923→| Class | Example | Default approach |
   924→|---|---|---|
   925→| Critical business | invoice/payment/audit | long-term retention by policy |
   926→| Operational history | session history | configurable |
   927→| High-volume telemetry | bandwidth samples | short/medium with aggregation |
   928→| Security telemetry | NAT/security logs | policy/legal dependent |
   929→| Debug | diagnostic captures | short retention |
   930→
   931→Never hard-code deletion without an explicit retention configuration and audit requirement.
   932→
   933→---
   934→
   935→# 37. PARTITIONING GUIDANCE
   936→
   937→Consider time partitioning for measured high-volume append tables such as:
   938→
   939→- accounting events;
   940→- session history;
   941→- audit log;
   942→- NAT logs;
   943→- syslog;
   944→- telemetry samples;
   945→- notification delivery history.
   946→
   947→Partition only where operational/query benefits justify the complexity.
   948→
   949→Partitioning strategy is a performance decision validated by benchmark, not a visual architecture preference.
   950→
   951→---
   952→
   953→# 38. DATA ACCESS PATTERNS
   954→
   955→Domain services should access data through explicit repositories/query services.
   956→
   957→Do not allow arbitrary pages to perform direct SQL against every table.
   958→
   959→Required read patterns should be optimized intentionally:
   960→
   961→- list queries;
   962→- detail queries;
   963→- dashboard aggregates;
   964→- active-session lookups;
   965→- reporting queries;
   966→- background jobs.
   967→
   968→Use specialized read models when the normalized transactional model cannot support dashboard/report workloads efficiently.
   969→
   970→---
   971→
   972→# 39. MIGRATION FROM LEGACY MODEL
   973→
   974→Migration sequence:
   975→
   976→1. inventory legacy models;
   977→2. reconcile source model names;
   978→3. classify every model;
   979→4. map to canonical entity;
   980→5. define transformation;
   981→6. migrate reference/master data;
   982→7. migrate transactional data;
   983→8. migrate accounting/history;
   984→9. verify counts/checksums/business totals;
   985→10. enable dual-read or validation where required;
   986→11. cut over;
   987→12. preserve rollback path;
   988→13. deprecate legacy structures.
   989→
   990→No direct blind Prisma schema copy is accepted as the final architecture.
   991→
   992→---
   993→
   994→# 40. DATABASE CONNECTION GOVERNANCE
   995→
   996→Requirements:
   997→
   998→- bounded connection pools;
   999→- separate pools by workload class when justified;
  1000→- query timeouts;
  1001→- transaction timeouts;
  1002→- retry policy only for retry-safe operations;
  1003→- connection leak detection;
  1004→- slow query visibility;
  1005→- migration locking discipline.
  1006→
  1007→There is never one connection per subscriber, packet, request, or session.
  1008→
  1009→---
  1010→
  1011→# 41. DATABASE HIGH AVAILABILITY
  1012→
  1013→Production deployment may use replication/HA according to deployment size.
  1014→
  1015→The application must understand database role/availability states.
  1016→
  1017→A database outage MUST NOT cause a packet-path crash loop.
  1018→
  1019→The gateway must fail according to explicit control-plane/data-plane degradation rules defined by the gateway architecture.
  1020→
  1021→---
  1022→
  1023→# 42. DATA PRIVACY
  1024→
  1025→Sensitive fields should be classified:
  1026→
  1027→- credentials;
  1028→- secrets;
  1029→- payment references;
  1030→- personally identifiable information;
  1031→- subscriber identity data;
  1032→- support notes;
  1033→- device credentials;
  1034→- AI-sensitive data.
  1035→
  1036→Use field-level access controls, redaction, encryption-at-rest where appropriate, and strict export permissions.
  1037→
  1038→---
  1039→
  1040→# 43. SCHEMA MIGRATION GOVERNANCE
  1041→
  1042→Every schema change must have:
  1043→
  1044→- migration script;
  1045→- rollback/forward strategy;
  1046→- compatibility assessment;
  1047→- index impact review;
  1048→- data-volume consideration;
  1049→- lock/downtime analysis;
  1050→- test migration;
  1051→- production verification.
  1052→
  1053→Never edit production schema manually as the normal deployment method.
  1054→
  1055→---
  1056→
  1057→# 44. DATA ACCEPTANCE GATES
  1058→
  1059→Schema implementation is not complete until:
  1060→
  1061→- all canonical domains have owners;
  1062→- source model reconciliation is complete;
  1063→- all critical foreign keys/uniques are defined;
  1064→- active session lookup paths meet target latency under load;
  1065→- high-volume tables have retention plans;
  1066→- financial calculations are reproducible;
  1067→- audit is immutable;
  1068→- outbox is reliable;
  1069→- migrations are tested;
  1070→- production PostgreSQL backups/restores are tested.
  1071→
  1072→---
  1073→
  1074→# 45. FINAL DATA PRINCIPLE
  1075→
  1076→```text
  1077→Business truth → PostgreSQL
  1078→Live session truth → Session Engine
  1079→Dataplane truth → VPP
  1080→Historical evidence → durable history/log stores
  1081→Metrics → observability backend
  1082→Cache → optional acceleration, never hidden authority
  1083→```
  1084→
  1085→The database is the durable memory of the product, not the packet processor.
